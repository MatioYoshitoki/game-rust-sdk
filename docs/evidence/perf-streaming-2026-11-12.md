# SDK 性能定位与流式序列化优化（0.184.0）

2026-11-12，SDK 0.183.0 → 0.184.0。性能工程闭环的**定位与优化两步**：在 [合成基线压测](bench-baseline-2026-11-12.md)（观察）之后，用采样定位热点并实施首个优化，同负载 A/B 验证。仍非 R6.3 验收。

## 定位（macOS `sample`，release 带 debug 符号）

- **引擎计算远未饱和**：4 房持续负载下，内核主线程 99.5% 的样本阻塞在 stdin read / channel recv——30ms 步预算内实际计算只占个位数毫秒，单进程余量巨大
- **唯一显著热点在输出路径**：忙碌窗口的可见样本几乎全部落在 `serde_json::value::Value` 的序列化/析构、`String` 克隆与 stdout 写出——JSONL 响应先经 `json!` 宏把整批输出（含全量/增量快照）展开成 `Value` 树（大量分配），再序列化、再整树丢弃。**结构体 → Value 树 → 字节串的双重转换**是纯浪费

## 优化（`src/bin/kernel-host.rs`）

响应改为**类型化 + 流式序列化**：`Response` 枚举（untagged，字段形状与历史 `json!` 包装逐字节一致）+ `serde_json::to_writer` 直写 stdout，信封前后缀由 `write!` 拼接。`json!` 调用清零，不再构建任何 `Value` 树。wire 字节不变（真实宿主栈 246 项 Node/H5 测试与全部场景测试原样通过）。

## A/B（同负载、同机、每房独立进程、120s/档）

| 档位 | CPU 均值 | RSS 均值 | drain p99 |
|---|---|---|---|
| 16 玩家 | 9.1% → **7.3%**（−20%） | 22.1 → **18.6 MB**（−16%） | 13.1 → 15.1ms（噪声区间） |
| 24 玩家 | 10.9% → **8.9%**（−18%） | 31.7 → **27.5 MB**（−13%） | 10.3 → 10.4ms |
| 36 玩家 | 19.5% → **14.2%**（−27%） | 54.7 → **46.0 MB**（−16%） | 10.1 → 13.4ms |

CPU 与内存双降且随档位放大（输出量越大收益越大）；drain p99 在 10~15ms 运行间波动，无退化结论。

## 剩余性能工作（未做）

criterion 微基准与回归门禁、单进程多房极限（当前架构每房一进程）、2 小时长稳泄漏斜率、`to_value` 残余调用点（checkpoint 摘要路径，量小）、真实 Socket 传输层。前述观察也表明：在合成负载下**计算不是瓶颈，输出与进程模型才是**——后续优化应聚焦输出编码与单进程容量。
