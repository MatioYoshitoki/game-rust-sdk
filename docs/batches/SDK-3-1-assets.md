# SDK-3-1 通用入场成本与结算收益

本批先冻结需求与验收，再实现。沿用 SDK-2 现有玩法、公式和状态机，新增可选的通用资产业务契约。第二款游戏及玩法结果类型在后续安排。

## 范围与版本

- crate 升至 0.2.0。旧配置 schema 1/2 对应协议 1，旧业务请求、回执、事件与检查点语义保持。新配置 schema 3 必须声明 `asset_contract:{entry_cost_asset_id,reward_asset_id}`，对应协议 2；不得静默跨协议选择。
- 协议 2 使用 `LoadAssets`、`AssetsLoaded` 与类型化 `CommitAssets`，事务区分 Admission、Settlement、Compensation。成本/收益为按 asset_id 严格排序、唯一、正数量的有限资产行；事务原子执行，预期 revision、operation_id、attempt_id、提交证明及原入场补偿关联保持。
- 入场扣除携入物品及配置成本资产；结算返还保留物品并增加配置收益资产；补偿精确返还原入场扣除的两类资产。0 数量行省略，物品数量与收益仍由 Rust 根据当前配置/战果冻结。库存收支摘要保留 carried/looted/kept/dropped 和现有机制证明用于恢复校验。
- 本批复用现有数值配置（`carried_quantity`、`params.entry_years` 与积分/收益公式），新增资产 ID 映射；旧参数名、战斗属性/视图、Outcome 和具名机制 DTO 的进一步收敛后续处理。成本和收益 ID 必须不同，且不得与配置物品 ID 冲突。
- 账户资产事实有明确上限、严格排序和唯一性，须包含携入物品及成本资产。错误身份、协议、事实或资产不足不得触发扣费。宿主不重新计算奖励，不把未知结果当作未提交。
- 检查点保存实际发出的原版本冻结正文和原回执；恢复时按对应版本严格校验再复用既有责任状态机。新协议不能把旧正文解释成新资产事务；已冻结金额、查询、重试和人工核对均保持原业务身份。
- 使用现有测试场/地图配置的变体验证，提供可执行的资产宿主及本地持久账本验收；旧 H5/最小宿主继续使用协议 1。生产库存、跨机接管与正式发布另行验收。

## 验收

| 编号 | 必须成立 |
|---|---|
| AS01 | schema/协议精确匹配；资产 ID、引用冲突、未知字段、数量、行数、顺序、重复行非法时原子拒绝。原 20 个样例原文/hash 保持。 |
| AS02 | 协议 2 完成入场、就绪、战斗/拾取、撤离与死亡；仅扣配置资产并按 Rust 冻结数量增加收益；替换资产 ID 无需改代码。宿主业务正文没有修为/年限字段。 |
| AS03 | 账户事实身份/资产不足拒绝，无部分扣款；重复创建、输入、存储执行和回执不重复生效；整批资产和提交证明原子落账。 |
| AS04 | 已提交但结果 Unknown，查询原事务取得同一证明；权威未提交可按原 ID/正文有限重试；拒绝后进入原责任核对，不能换 ID 发奖。 |
| AS05 | 就绪前关闭精确补偿入场，激活后关闭按原冻结结算，Closed 可携带未决，继续处理后 World=0/未决=0。 |
| AS06 | 持久冻结后进程重启：已提交/未提交结算、入场中断退款、核对结果与再次重启均按原 ID/数量一次执行；不恢复 World 或重算奖励。 |
| AS07 | 恢复中篡改资产 ID/数量/摘要/协议、重复/乱序资产行、提交凭据或错误原入场关联，即使重算检查点摘要也拒绝；失败不部分初始化，合法恢复仍可继续。 |
| AS08 | 旧协议配置、历史冻结请求和旧检查点继续通过原回归；SDK-2 仓库外消费方、B1、持久恢复、H5 基线通过；记录同源源码/配置/二进制证据。 |

实现中不得改变旧玩法公式，或用任意 JSON 业务载荷绕过有限事务目录。执行结果单独记录，未执行项保持待验。
