# SDK-3-2 终局结果与结算策略解耦

先冻结本批范围与验收，再实现。沿用现有撤离、死亡两条 Rust 终局触发机制，公开结果与结算策略通过配置绑定。

## 范围与兼容

- crate 升为 0.3.0。schema 1/2、3 继续分别使用协议 1、2，原消息正文、资产语义和检查点保持；schema 4 必须同时声明 asset_contract 与 result_contract，使用协议 3。
- result_contract 为当前已注册的 extraction、death 触发分别指定 `{result_id,policy}`。结果 ID 为 1～64 UTF-8 字节、无控制字符、互不相同；未知触发、未知策略、缺失/多余字段及版本错配启动拒绝。
- 已注册策略为 `preserve`（完整保留物品，积分包含退出附加分，无结果折扣）和 `attrition`（按配置格子/数量损耗，积分不含退出附加分，使用配置结果倍率）。数值继续使用现有配置，旧版本按原路径执行。两条触发可以独立选择任一策略，包括选择同一策略；内核保持终局资格和时点判定权。
- 协议 3 沿用 LoadAssets/AssetsLoaded 与原子资产事务目录，结算使用 `ResultSettlement {expected_revision,credits,summary}`。summary 冻结 `{result_id,policy}`、物品收支及现有机制证明；结算请求和对应事件不要求宿主解释 Extraction/Death。入场与补偿保持同一有限事务能力。
- Rust 根据已选策略计算损耗及收益，冻结结果和资产，宿主只执行原事务并报告证明。客户端不能提交结果 ID、策略、金额或直接终局事实。
- 重试、查询、关闭与重启沿用原业务 ID、完整结果和策略；按原配置 hash 恢复。已释放 World 不重建，已冻结责任不按新配置映射改名或重算。
- 新结果契约泛化业务边界；现有终局触发、玩法输入、成长视图字段和参数名称继续沿用。胜负/竞速等新触发机制、更多结算策略、生产存储和第二款游戏另批验收。

## 验收标准

| 编号 | 通过条件 |
|---|---|
| RS01 | schema/协议/策略目录匹配；非法/重复/超长结果 ID、未知策略/触发、额外字段原子拒绝，无静默回退。原 20 份场景和协议 2 样例 raw/hash 保持。 |
| RS02 | 默认绑定完整完成战斗、拾取、撤离/死亡，资产与原版本相同；请求/事件只含配置结果 ID 和策略，修改结果 ID 无需修改源码。 |
| RS03 | 交换策略，以及两条路径选择同一策略：结算损耗和奖励遵循策略，终局触发时点仍由 Rust 判定；覆盖单物品及 PVE 多物品收支/消费证据。 |
| RS04 | 结算结果、策略与资产一次冻结；重复创建/输入/事务执行/回执一次生效；Unknown 查询同一证明，fencing 未提交按原正文重试，拒绝保留原核对责任。 |
| RS05 | 未就绪关闭仅补偿入场；激活后关闭沿当前死亡触发的配置策略结算；Closed 后继续收尾，最终 World=0、未决=0；待核对责任不得假报成功。 |
| RS06 | 结算持久前后、入场/补偿中断及人工核对后连续重启，原结果 ID/策略/金额/operation ID 不变且一次提交；修改外部结果配置不影响旧责任。 |
| RS07 | 恢复拒绝未知结果、结果与策略不匹配、混用旧/新正文、非法收支/奖励/凭据；重算检查点摘要仍执行语义校验，失败不部分初始化。摘要不构成抗特权主机篡改签名。 |
| RS08 | 原协议 1/2、B1、SDK-2 消费方、SDK-3-1 资产闭环、配置加载、持久恢复和 H5 基线通过；证据绑定源码与配置版本。 |

专项入口：`python3 scripts/verify_sdk_3_2.py`。执行结果独立记录，未执行项保持待验。
