# B2-2：外部业务超时收尾

日期：2026-11-02。状态：受控验收通过，见 [执行记录](../evidence/B2-2-io-deadlines-2026-11-02.md)。范围：用户已授权外部加载、扣费、结算、查询与补偿的有限等待。持久责任账、进程重启恢复和生产数据库耐久性仍属下一小步。

## 采用口径

- Rust worker 使用自身 `Instant` 单调时钟处理 I/O 期限，独立于玩法逻辑时间。普通模式和加速玩法验证模式的 I/O 期限都按真实经过时间计算；Preparing、Draining、Closed、Faulted 仍处理未决 I/O。Client 不增加 tick/时钟/内部阶段入口。
- 单次自动 I/O 等待 5000ms，从 Rust 发出冻结请求起计算。合法重试只在原业务 ID 下增加 attempt，并重新开始该次等待；无效回执、重复 unknown、乱序查询和时钟回退不能延长期限。未收到回执不能当作 not_committed。
- 读取超时直接终止准入、退休该读取，不扣费，也不再接纳迟到读取去发起入场。已证明的读取 unknown/失败仍沿用原有有限重试逻辑。
- 扣费、结算或补偿超时按未知结果处理，先查询原业务 ID，并走现有 close 释放 World。扣费迟到提交只履行原入场补偿，不重建角色；结算迟到提交只履行冻结奖励，不重新计算金额。
- 查询超时/仍未知只生成一个对账请求。普通自动重试最多三次，且必须已有权威、隔离迟到写入的未提交证明。查询绑定发起时的原尝试；旧查询的负结果不能推进新尝试。进入人工核对后，迟到负结果不能再发起写入或取消冻结责任。
- 已进入 Draining 的 World 最多保留 15000ms 服务时间供正常提交/核对，之后即使等待人工也释放 World；责任留在 World 外。人工核对没有自动成功或无界自动重发，必须取得原冻结意图的提交证明。
- 输出空间不足时使用保留槽位先关闭 World，并保留到期 I/O 责任，待输出可用后继续查询/核对；不以静默丢弃责任来腾出容量。实例 Faulted 后仍处理冻结 I/O，不通过超时恢复 World。
- 准入仍在等待读取/扣费时可刷新换代，保持原请求、原业务和一次扣费；World 创建后仍要求新代完整状态、Foreground/sent/ready。未创建 World 时不消耗战斗重连的逻辑保留窗口。
- 准入完成后，初次客户端也有 30 秒逻辑就绪窗口；创建请求成功但客户端未连接/未 ready 时，按未激活入场补偿并回收，避免无人加入的 World。这个客户端窗口沿用重连逻辑时间口径，与上面的真实 I/O 等待时间区分。

## 验收

1. 4999ms/5000ms 边界、玩法暂停/加速/关闭后的期限、无效/迟到/重复回执和单调时钟回退都得到确定结果。
2. 静默加载结束后无扣费、无 World、无未决读取；迟到加载不能重新准入。
3. 扣费/结算/补偿无回执时，先查询、不重复写。权威迟到提交、查询提交或人工证明均只应用一次；关闭后不复活。
4. 查询也无回执时进入明确未决状态，World=0，冻结金额和原业务 ID 保留；无证明不能显示成功。
5. 15 秒结算期限不依赖玩法 tick；迟到负查询不跳过尝试；输出背压不丢失超时责任。
6. 真实 H5 复现静默、延迟和完全丢回执，仍可核对、刷新、收尾；原 B1、B2-1 和等距操作回归通过。

验证入口：`python3 scripts/verify_io_timeouts.py`；机器报告绑定本轮 Rust、H5、适配器和验证脚本。配置和来源包保持冻结，不能借此签收生产 I/O 持久性。
